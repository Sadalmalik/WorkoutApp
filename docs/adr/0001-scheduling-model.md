# 0001. Расписание как подключаемая стратегия, отделённое от программы

## Контекст

«Какая тренировка сегодня» можно определять по-разному: жёстко по календарю; по факту завершения; гибридом (тренировка ждёт завершения, дни отдыха продвигаются по календарю). Пользователь ещё не выбрал предпочтительный режим и хочет пробовать в бою. Программами обмениваются файлами экспорта, поэтому форма сохранённых данных «утекает» наружу, и жёстко зашитая модель была бы дорога в развороте.

## Решение

Разделяем две сущности:

- **Программа** — чистая модель данных (планы, ротация, блоки, упражнения, сетки прогрессии). Не знает, как её проходят.
- **Расписание** (Scheduler) — подключаемая стратегия за единым интерфейсом:
  - определить текущую тренировку и продвигать состояние (update);
  - сохранять/загружать собственное состояние отдельной структурой в сейве;
  - откладывать/пропускать тренировки.

Программа несёт поле «рекомендованное расписание» (идентификатор стратегии — это данные, не код). При запуске программы пользователь выбирает расписание, по умолчанию — рекомендованное программой; рантайм-состояние расписания (дата старта, курсор) — личное, отдельная структура в сейве. В Фазе 1 реализуем два расписания:

- **Календарное**: дата → день плана через дату старта и длину цикла; неначатая пропущенная тренировка **сгорает**.
- **Гибридное**: тренировка **ждёт** завершения (не теряется при пропуске зала), дни отдыха продвигаются по календарю.

Персистентность сессии **ортогональна** расписанию: незавершённая сессия живёт независимо и переживает смену суток. Вопрос «продолжить/завершить» задаётся при смене суток **или** после N часов без залогированного сета (чтобы не мешать посреди тренировки).

## Рассмотренные альтернативы

- **Единая захардкоженная модель** — проще, но необратима и ломает экспортные файлы при смене семантики.
- **Чистый календарь** (как v1) — теряет прогресс при пропусках зала.
- **Чистое завершение** — дни отдыха теряют смысл, а «сегодняшняя» тренировка протухает после долгого перерыва.

## Последствия

- Обратимость перестаёт быть проблемой: программа переключается между экземплярами расписаний.
- Миграция между режимами при необходимости — одноразовый конвертер состояния к дефолтному (календарному); добавление нового режима не трогает существующие.
- Каждое расписание хранит собственную структуру состояния в сейве, что нужно учитывать в формате экспорта/импорта.
