# Отчёт: реализация Workout App v2.0 — Фаза 1

Дата: 2026-08-25. Ветка: `feat/workout-app-v2` (слита в `main` fast-forward). Итог: 14/14 тикетов `done`, спека `done`, 243 теста ядра зелёные, сборка без предупреждений.

## Метод

Спека разбита на 14 тикетов с явным графом блокировок. Каждый тикет реализовывал отдельный фоновый агент в собственном git worktree на ветке `impl/NN-*`; по завершении работа вливалась в интеграционную ветку, статус тикета переводился в `done`, пересчитывался фронтир. Лимит — не более 3 агентов одновременно. Общая архитектурная заметка-указатель (`_impl-notes/ARCH.md`) фиксировала инварианты, чтобы агенты не переоткрывали контекст.

Критический путь оказался линейным: `01→02→03→04→05`. Параллелизм — на веере после 05, организованном в 3 трека, чтобы правки одного файла не пересекались:
- Трек A (экран тренировки, последовательно): 06 → 07 → 08.
- Трек B: 09.
- Трек C (экспорт/импорт): 11 → 12 → 13.
- 10 (вес тела) — параллельно 02; 14 (доступность) — в конце, после 07/08/09.

## По тикетам

- **01 — Скелет и префактор.** Удалён код v1 (Google Sheets/Forms, очередь, `GEMINI_API_KEY`). Заложена граница чистого TS-ядра `src/core/` с портами `Clock`/`Storage` (по две реализации: system/localStorage и fixed/in-memory), модель `SaveData` со `schemaVersion`, интерфейсы стратегий `Scheduler`/`Report`/`Progression` (контракты без реализаций), hash-роутер, нижняя навигация с заглушками, PWA (vite-plugin-pwa), vitest. Фундамент для остальных 13.
- **02 — Каталог упражнений.** Модель `Exercise` (id, name, zone, videoLinks, isBodyweight, equipmentWeightStep, notes, muscleRefs). CRUD через `Storage`, поиск `searchExercises` (регистронезависимый substring + матч по зоне), автоподсказка зон. Кнопка «создать новое» — только после пустого поиска с подтверждением (устранение корневой причины дублей v1).
- **03 — Редактор программ.** Модель строго по глоссарию: `Program → Plan → PlanDay(union rest/workout) → Workout → Block → BlockExercise` со статической целью `{weight,reps}`. Суперсет определяется числом упражнений в блоке. `recommendedSchedulerId` в программе. Валидатор структуры + ссылочная целостность против каталога. Линейный редактор с суперсетами и интервалами.
- **04 — Расписание, Home, запуск.** Две реализации `Scheduler` за единым интерфейсом: `CalendarScheduler` (дата→день плана, пропущенная неначатая тренировка сгорает) и `HybridScheduler` (тренировка ждёт, отдых по календарю). Реестр по `SchedulerId`. Состояние расписания — отдельная структура в сейве. Машина состояний Home (начать/отдых/тренировка/пауза/завершено), попап управления программой по двойному тапу.
- **05 — Сессия и экран тренировки.** Ядро сессии ортогонально расписанию: снимок тренировки в `Session`, лог сетов в историю `results`, авто-завершение и продвижение расписания. Ad-hoc-упражнение не двигает курсор, засеряет таймлайн. Триггер «продолжить/завершить» — по смене суток ИЛИ порогу N часов. Экран тренировки — фиксированный вьюпорт с чёткими слотами под виджеты 06/07/08.
- **06 — Таблица результатов.** Виджет ввода (`−/+` + точный ввод, вес сохраняется между сетами, повторы очищаются) и прокручиваемая таблица с правкой/удалением сета. Добавлены `editSessionSet`/`removeSessionSet` (синхронизируют `loggedSets` и `results`).
- **07 — Таймлайн.** Чистые селекторы (`timelineModel`) + компонент: кружок=упражнение, блок=столбик, линия=междуБлоками, закраска блока целиком, отложить=своп со следующим, засеривание при ad-hoc. Состояния кружка различимы формой (контур/заливка/маркер).
- **08 — Таймер отдыха.** Ядро без дрейфа: отсчёт от абсолютной метки `endAt` через `Clock`. Круг с кнопкой внутри, инкременты ±1/10/30/60, звук (Web Audio) + вибрация, предзаполнение интервала из курсора. Браузерные API вынесены в UI-модуль, ядро чисто.
- **09 — Отчёты и графики.** Интерфейс `Report` + два отчёта («макс. вес за день», «макс. вес + повторы»); для bodyweight ключевая линия — повторы. Агрегация точек дня, детекция рекордов, сводка сессии — чистые функции ядра. SVG-график с привязкой к правому краю. Экран результата (рекорды→сводка→графики) и общий экран Results.
- **10 — Лог веса тела.** `BodyweightEntry`, операции через `Clock`/`Storage`, попап по кнопке «перо».
- **11 — Экспорт.** Два режима (полный; «программы+упражнения» со сбором транзитивных ссылок упражнения→мышцы). Формат `ExportDocument` со `schemaVersion` — контракт для импорта.
- **12 — Импорт.** Двухпроходный пайплайн: дедуп по именам («дубль/разные» + перевязка ссылок), затем мерж с diff и политиками (пропустить/перезаписать/оставить оба). Результаты/вес — union с дедупом; settings/scheduler/session — замена. Единая перевязка ссылок в `applyImport`.
- **13 — Импорт CSV v1.** RFC-4180 парсер, маппинг вкладок «Exercise List»/«Results» в модель, прогон через пайплайн 12 без дублирования логики мержа.
- **14 — Доступность.** Палитры под типы дальтонизма (Okabe–Ito) через `data-palette`, тема light/dark/system, `updateSettings`, аудит «цвет — не единственный носитель» по таймлайну/графикам/таймеру.

## Возникшие проблемы и решения

1. **node_modules в worktree (Windows).** node_modules gitignore-ится и в worktree отсутствует; полная установка в каждое из ~15 деревьев — сотни МБ. Решение: единая установка + junction (`mklink /J`) в каждом дереве. Подводный камень: junction ведёт Node ESM к реальному пути, и если общая папка называется не `node_modules` (пробовал `_shared_nm`), hoisted-пакеты (`@vitest/utils`) не резолвятся → `ERR_MODULE_NOT_FOUND`. Исправлено переименованием общей папки в `node_modules`. Зафиксировано в auto-memory.

2. **Месячный лимит расходов посреди прогона.** Агенты тикетов 08 и 12 были прерваны API-ошибкой лимита. После поднятия лимита пользователем оба возобновлены сообщением с сохранённым контекстом (не холодный перезапуск): 12 имел 2 коммита ядра + незакоммиченный UI — продолжил ровно с места; 08 стартовал с чистого дерева. Потерь нет.

3. **Конфликты мержа.** Веерные тикеты параллельно правили общие файлы (`src/core/index.ts`, `src/ui/App.tsx`, `src/ui/screens/index.tsx`, `src/ui/styles.css`). Разрешались вручную при вливании каждого тикета; барели и CSS — как правило аддитивно, спец-случаи экранов (Settings из 11/12, Results из 09) — объединением веток рендера.

4. **Скрытая CSS-регрессия.** При автоматическом стрипе конфликт-маркеров (`sed`) в мерже тикета 09 потерялась закрывающая `}` у правила `.setinput` — весь последующий CSS оказался невалидно вложенным. Обнаружено по предупреждению esbuild `css-syntax-error` во время мержа 08; локализовано подсчётом баланса скобок, восстановлено тело `.setinput` из ветки 06. После этого в процесс добавлена проверка баланса `{}` и `grep` по warn при каждой сборке.

5. **Граница суток — UTC.** Агенты 04/05 реализовали `dayIndex` через UTC-полночь ради детерминизма тестов и отметили это как точечно заменяемое. Оставлено как есть (см. нерешённое ниже).

## Код-ревью и новые задачи в процессе

Проведено двухосевое `/code-review` (Standards + Spec) параллельными агентами. Ядро признано чистым (протечек DOM/localStorage/Date.now в `src/core/**` нет). Найдено и **исправлено единым фикс-агентом** 6 пунктов (новые задачи, возникшие по итогам ревью):

- **S1 (CSS-дубли от мержа).** `.btn`/`.btn--primary`/`.btn--ghost`/`.workout` были определены дважды с конфликтующими значениями. Сведены в один набор; пунктирная add-affordance вынесена в отдельный класс `.btn--add`; контейнер экрана тренировки переименован `.workout → .workout-screen` (два разных layout-контракта под одним именем).
- **SP1.** Порог N часов (`continueThresholdHours`) не редактировался в UI — добавлено поле в настройки.
- **SP3.** «Начать следующую» в день отдыха показывалась и для календарного режима, где pull-forward бессмыслен — ограничено гибридным расписанием.
- **SP4.** Гибридный `skip` двигал на 1 день плана — теперь доходит до следующей тренировки за один вызов (с обновлением тестов).
- **SP5.** Обязательный сигнал таймера ловился 250-мс поллингом, тротлящимся в фоне — переведён на планирование бипа на абсолютное время через аудио-часы Web Audio (не тротлится), с перепланированием при докрутке/паузе.
- **SP2.** Добавлен запрос разрешения на системное уведомление по жесту старта.

**Новая задача от пользователя (после реализации):** конфигурация сборки под GitHub Pages. `base` был `/`, что ломало проектный сайт в подпапке. Установлен относительный `base: './'` (и `start_url`/`scope` в манифесте) — одна сборка работает и на GH Pages, и через локальный статический сервер.

## Нерешённые / отложенные задачи

Осознанно не сделано в этой фазе:

1. **S2 (рефактор).** Паттерн `load→mutate→save` повторяется в 12+ местах ядра, не вынесен в общий хелпер. Пропущен как косметика с риском лишнего churn — не дефект.
2. **Wake-lock таймера** при заблокированном экране — остался `TODO` в `restTimerSignal.ts` (спека допускает отложение; звук+вибрация+отсутствие дрейфа реализованы).
3. **Юнит-тесты UI-компонента таймера.** Логика ядра таймера покрыта, но `RestTimer.tsx` (планирование сигнала, SP5/SP2) проверен только typecheck+build — браузерные API без DOM-теста не покрываются.
4. **Граница суток — UTC, а не локальная полночь.** Для ночных тренировок, пересекающих локальную полночь, триггер «продолжить/завершить» и продвижение отдыха срабатывают по UTC. Точечно заменяемо в `scheduler/day.ts`, интерфейс не затрагивается. Требует решения пользователя (локальная TZ vs детерминизм).
5. **Удаление сета не откатывает курсор** плана (осознанный scope тикета 06): при удалении лишнего сета счётчик «сет N/M» в шапке не уменьшается.
6. **Метки отчётов в переключателе статичны** независимо от bodyweight (семантика адаптируется на уровне подписей линий, а не названий отчётов) — отмечено агентом 09 как возможное уточнение.
7. **Остаток уборки.** Пустой каталог `_wt/03-program-editor` не удалён (Windows-хендл «busy»); безвреден, удалится позже.
8. **Пуш и PR.** `main` на 60 коммитов впереди `origin/main`; пуш и GitHub-PR не делались (`gh` не установлен, пуш пользователь не запрашивал).
9. **Авто-деплой.** Actions-воркфлоу для GitHub Pages не заведён (предложен как опция).

## Out of Scope (Фаза 2+, по спеке)

Сетки прогрессии и адаптивный сдвиг (в Ф1 — только статические цели); мультиплан и ротация; каталог мышц (UI/наполнение) и метрика баланса; отчёт/график веса тела; режим графика «за всё время», зум, разворот по тапу; удаление прошлых результатов на экране статистики; журнал заметок; fuzzy-поиск. Структурные заделы под них (массив `plans`, `target: ProgressionTarget`, `muscleRefs`, интерфейсы стратегий) заложены, реализация — отдельными спеками.
